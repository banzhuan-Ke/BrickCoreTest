# 性能测试

## 适用场景

对 HTTP 接口进行压力测试：吞吐量、响应时间分位、错误率；支持多接口混合场景、梯度加压、分布式 Worker。

## 使用前准备

| 项 | 说明 |
|----|------|
| 项目与环境 | 已配置，Host 指向压测目标（**勿对生产误压**） |
| 接口用例 | 在 **接口自动化 → 用例管理** 中维护被压接口 |
| 执行机（**必需**） | 须上线压测 Worker（**BrickCoreRunner** 或 **BrickCorePerf**）；平台不本机直跑施压 |

## 基本流程

```
场景管理 →（启动执行机）→ 执行压测 → 执行记录 / 报告对比
         ↘ 定时压测（可选）
```

## 场景管理

**路径**：**性能测试 → 场景管理**（界面标题「性能测试场景」）

列表页可展开 **「常见性能测试场景：目的与平台怎么配」**；新建/编辑页另有 **「压测模式说明」**。下面与界面说明一致，便于对照配置。

### 常见测试场景（目的 → 怎么配）

| 常见场景 | 目的 | 平台大概怎么配 |
|----------|------|----------------|
| **冒烟试跑** | 确认接口通、脚本与环境无误，再做正式加压 | **固定模式**：小并发（如 5）+ 短时长（如 30 秒） |
| **负载 / 长稳** | 目标并发下观察延迟、错误率与稳定性（可到数十分钟～数小时） | **固定模式** + 目标并发 + 持续时长；建议设 **Ramp-up**；长稳可开 **错误率熔断** |
| **容量 / 探极限** | 找性能拐点与大致最大可支撑并发 | **梯度模式**：分阶段递增（如围绕已知 40：20→30→40→50→60）；看错误率与 P95 突变点 |
| **峰值 / 尖峰** | 验证高峰负载能否扛住 | **固定**高并发短时长，或梯度快速摸高；错误率阈值可设约 50% 自动停 |
| **瞬时 / 吞吐** | 总量可控的一批请求，适合回归与版本对比 | **循环模式**：并发 × 每人循环次数，打完即停 |
| **业务链路** | 按真实用户路径评估端到端容量 | **链路固定 / 链路循环**：从接口套件导入步骤，配置间隔与变量传递 |
| **混合流量** | 多接口接近真实配比 | 非链路下添加多用例，设 **随机权重** 或 **固定比例** |
| **流式 / SSE** | 评估问答流式首字、阶段耗时等 | **流式阶段**（每人 1 次，非持续加压）；**持续加压**请用固定/循环/梯度并打开 **流式问答** |

**通用配置**：Ramp-up（加压）、Warmup（热身）、错误率熔断、**性能验收目标**、请求间隔（固定/随机毫秒）、CSV 参数化等，在场景编辑页配置。也可用 **AI 创建** 一句话生成草稿（只引用项目内已有用例/套件），确认后再落库细调。

### 压测模式

| 模式 | 说明 |
|------|------|
| **固定模式** | 固定并发 + 持续时长（秒） |
| **循环模式** | 固定并发 + 每用户循环次数 |
| **梯度模式** | 多阶段递增并发与时长 |
| **流式阶段** | 每虚拟用户 **1 次** SSE（非持续加压），采集阶段耗时；持续加压请改用固定/循环/梯度 + **流式问答** |
| **业务链路** | 多 API 步骤顺序执行，步骤间 extractors 传参（登录→业务接口等） |

固定/循环/梯度模式还可勾选 **流式问答**：在持续压测中对指定用例走 SSE 引擎。报告中会同时展示 QPS/RT 与 SSE 阶段摘要，请对照阅读。

> **流式开关**：关闭「流式问答」会清除 `stream_profile`，执行与报告按**普通 HTTP**（QPS/RT）；仅当次配置含流式或模式为「流式阶段」时才展示 SSE 阶段区。接口若返回普通 JSON 却开着流式，会判失败并提示关闭流式或更换解析器（执行机需更新至配套 Perf/Runner 包）。

**流式 / 链路专属配置**

| 参数 | 说明 |
|------|------|
| `stream_profile.parser_id` | 流式解析器（默认 `qa_sse_v1`） |
| `stream_profile.timeout_seconds` | SSE 读空闲超时（默认 600s，非整段回答上限） |
| `request_detail_level` | 执行时选择 **简略** / **详细**（详细模式额外保留成功请求 HTTP trace，不影响 QPS/RT） |
| 链路步骤 | 每步可选是否走流式；阶段 sync 在本机/单 Worker 内同步 |

**业务链路搭建提效**：场景编辑支持「从接口套件导入」「保存/应用链路模板」；用例可打业务标签（如 `perf`）并在链路步骤下拉按标签筛选；缺失用例会红字提示并拦截保存；从套件导入后若源套件变更会黄条提示可重新导入；接口调试可「保存为用例」并建议 JSONPath 提取项（需 `aerich upgrade` 启用模板表）。

| 参数 | 说明 |
|------|------|
| 并发用户数 | 1～1000（视环境与 Worker 能力） |
| Ramp-up | 爬坡时间（秒），用户逐步启动 |
| 目标 Host | 可覆盖环境 Host |
| 错误率阈值 | 超过可自动停止（若配置） |

**关联接口用例**

- 添加多个 **API 用例**，设置 **权重** 或 **固定比例**（如 1:2 严格轮询）
- 可配置单接口请求间隔：固定毫秒，或随机区间（如 1000~3000ms，类似 Locust `between`）
- 支持 **CSV 参数化**（轮询、独占、随机）：可 **下载模板**；选择/删除/改策略在编辑页为本地待定，**点场景「保存」才写入**；新建场景请先保存后再选 CSV
- CSV 引用：`${{csv.列名}}`；对列值做工具计算（如 MD5）写 `${{dt:md5|text=@csv.列名}}`（仅本场景绑定了 CSV 时有值；与同名环境变量隔离）
- 用例内可使用 **插入工具** 写入 `${{dt:...}}`；压测执行时与 `${{df:标签}}`、环境变量一并合并

### 执行场景

1. 先在 **执行机** 列表确认有在线 Worker（或按下方方式上线）
2. 在场景列表点击 **执行**
3. 选择 **执行环境**
4. 勾选执行机并确认分压（见下表）→ **确认执行**
5. 执行完成后到 **执行记录** 查看报告

**启动弹窗 · 执行器三列含义**

| 列 | 含义 |
|----|------|
| **本机上限** | 该执行机申报的最大并发能力，不是本次会启动的人数 |
| **分压比例** | 多机时按比例拆分场景并发（只比大小，如 2:1）；**仅勾选一台时禁用**，全部 VU 落在该机 |
| **本机分到** | 按比例落到本机的虚拟用户数（VU），合计等于场景需要的并发 |

> **施压方式**：压测一律由**在线 Worker**执行（BrickCoreRunner / BrickCorePerf），后端不再本机直跑。无在线执行机时**无法启动**（不会静默降级）。任务字段与上报契约见 [压测 Worker 协议](./perf-worker-protocol.md)。

## 执行机（Worker）

压测施压由**在线 Worker**执行（后端不再本机直跑）。**二选一即可**，不必两个都装。

### 方式一：BrickCoreRunner 完整客户端（含 GUI）

1. 安装 **BrickCoreRunner**（见 [执行器说明](./runner-client.md)）
2. 登录平台 → 执行角色选 **仅压测执行机** 或 **UI + 压测**
3. 选择 **压测项目**（须与平台顶部项目一致）→ 点击 **上线**
4. 在 **性能测试 → 执行机** 确认节点 **在线**（来源一般为「完整客户端」）

客户端会在 **当前会话日志** 实时显示压测进度（秒级 QPS、RT、错误率等）；完整日志见客户端安装目录下的执行机日志。下线时会自动向平台注销，无需等待心跳超时。

**Worker 注册鉴权（v1.5+，必填其一）**：

| 方式 | 适用 | 如何配置 |
|------|------|----------|
| `X-Runner-Token` | BrickCoreRunner | 客户端上线后自动注入，无需手填 |
| 登录 JWT | BrickCorePerf（推荐） | `start-perf` 用平台账号密码登录后注入 `Authorization: Bearer`；须为该项目成员 |
| `X-Internal-Token` | 机房无人值守 / 命令行 | `.env` 的 `PERF_INTERNAL_TOKEN`，与平台 Backend 的 `INTERNAL_API_KEY` 一致 |

仅配置 `--token`（节点身份令牌）**不能**完成注册，会返回 401。多 Backend 副本时任务队列与秒级上报依赖 **同一 Redis**；默认 Redis 不可用会拒绝派发与秒级上报（可用 `PERF_ALLOW_INMEMORY_WORKER_QUEUE=1` / `PERF_ALLOW_INMEMORY_WORKER_REPORTS=1` 仅作单机调试）。

### 方式二：BrickCorePerf 精简压测包（CLI，体积小）

适合服务器常驻或本机只要压测、不要浏览器引擎：

1. 从 **设备管理** 下载 **精简压测包 Win/Mac**，或管理员将 zip 放到 `static/runner/`
2. 解压 → 运行 `start-perf.bat`（Windows）或 `./start-perf.sh`（macOS），按提示填写：
   - `PERF_MASTER_URL` / `PERF_TOKEN` / `PERF_PROJECT_ID`
   - **`PERF_USERNAME`**（平台登录账号，推荐）；启动时再输入密码换 JWT
   - 机房无人值守可改填 **`PERF_INTERNAL_TOKEN`**（与 `INTERNAL_API_KEY` 相同）
3. 执行机列表应显示来源「精简包」

也可复制 `.env.example` 为 `.env` 后手工修改。说明与冒烟清单见包内 `README-PERF.md`（仓库：`docs/其他文档/README-PERF.md`）。**勿将 Windows 包拷到 Mac 使用。**

### 对比

| 对比 | BrickCoreRunner | BrickCorePerf |
|------|-----------------|---------------|
| 压测引擎 | 官方闭源引擎（随包分发） | 同左 |
| 浏览器 / GUI | 有 | 无 |
| 报告与指标 | 一致 | 一致 |
| 项目 / Token | GUI | `.env` / 启动提示 |
| 典型来源标识 | `runner_client` | `perf_slim` |

压测引擎随 **BrickCoreRunner / BrickCorePerf** 官方安装包分发；请使用上述安装包接入，勿依赖源码自建引擎。协议对接见 [压测 Worker 协议](./perf-worker-protocol.md)。

### 何时需要 Worker

- **任意**压测启动（平台不再提供 Backend 本机直跑）
- 多机叠加 QPS、较高并发

## 执行记录与报告

**路径**：**性能测试 → 执行记录**

| 指标 | 说明 |
|------|------|
| QPS / 成功 QPS | 总吞吐 / 仅成功请求吞吐 |
| 响应时间 | Avg、P90/P95/P99 等（**含失败请求耗时**，错误率单独展示） |
| 接口维度分位 | 每个用例最多保留 **5000** 条 RT 样本（蓄水池采样）；总请求数 / QPS / 错误率不受影响 |
| 错误率 | 失败占比 |
| 趋势曲线 | 秒级 QPS、RT、并发 |

**报告页增强（v1.3.14+ Backend）**

- **SSE 阶段汇总**：问题理解首字、首字时间、思考耗时等（仅统计成功流式请求）
- **流式请求明细**：分页懒加载，支持全部/成功/失败筛选；思考过程、答案预览完整展示
- **HTTP 请求明细**：详细模式下成功 trace + 失败采样；可展开请求头/Body/完整响应
- **导出**：HTML（次要指标与趋势表默认折叠）、流式场景可 **导出 Excel**

支持 **多轮执行结果对比**；可 **发送报告邮件** 或开启完成后自动推送。

**基线、验收目标与熔断（三者独立）**

| 能力 | 作用 | 配置位置 |
|------|------|----------|
| **性能验收目标** `perf_targets` | 判断**本次**指标是否达到业务绝对值（如 QPS≥x、P95≤y）；报告确定性 pass/warn/fail | 场景编辑；启动时可覆盖；写入执行 `config_snapshot` |
| **基线** `baseline_policy` | 判断相对**历史黄金基线**是否退化 | 报告页「设为基线」+ 场景阈值 |
| **错误率熔断** `error_rate_threshold` | **运行中**错误率过高自动停止 | 场景编辑 |

- AI 分析只**解释** `target_evaluation`，不得自造「预期基准值 / 业务可接受范围」；未配置目标时报告明示「无法判定是否达标」
- 历史报告只读当时快照中的 `perf_targets`，事后改场景不影响旧记录

**基线与可信度**

- 报告页可将某次执行 **设为基线**；同场景后续报告自动对比，并可按阈值告警
- 已钉基线时展示 **相对基线趋势**（近期成功记录的 QPS / P95 / 错误率）
- 若执行后用例被修改，报告会提示 **用例已变更**（指标仍反映执行当时快照）
- 执行机列表对离线原因、引擎版本不匹配给出提示；执行弹窗展示各 Worker 引擎版本

## 执行机版本与部署配置

| 配置 | 当前推荐值 | 说明 |
|------|------------|------|
| BrickCoreRunner 客户端 | **≥ 1.6.1**（推荐） | 与 `runner_client/__init__.py`、`VERSION.txt` 一致；最低上线 `RUNNER_CLIENT_VERSION_MIN=1.3.8` |
| `RUNNER_CLIENT_VERSION_LATEST` | `1.6.1` | 服务器 `.env` / `docker-compose.yml` |
| `RUNNER_ENGINE_VERSION` | `1.6.1` | 与 `runner/settings.py` 中 `RUNNER_VERSION` 一致；引擎最低 `RUNNER_ENGINE_VERSION_MIN` 默认 ≥1.0.0 |

生产环境浏览器访问平台一般为 **80 端口**（Nginx），`--master` / 客户端服务器地址 **不要写 :8000**（8000 为容器内 Backend）。

## 定时压测

**路径**：**性能测试 → 定时压测**

配置 Cron / 固定时间自动执行场景。任务触发时须有在线 Worker，否则执行失败（后端不再自动回退本机施压）。

## 使用建议

- 压测前在 **低并发** 下验证用例与数据
- 与被测方确认窗口，避免影响生产
- **推荐** 使用 BrickCoreRunner 压测模式，便于选项目、看日志、一键下线
- CSV 数据注意脱敏

## 常见问题

**Q：Worker 显示离线？**  
检查 `--master` / 服务器地址、网络、`project-id` 是否匹配；客户端 v1.3.14+ 下线后应立刻离线。

**Q：客户端看不到压测日志？**  
确认已选压测角色并上线；平台触发压测后查看客户端「当前会话日志」或 `runner/logs/perf_worker.log`（v1.3.14+ 每秒输出 QPS/RT）。

**Q：QPS 很低？**  
提高并发或增加 Worker；检查被测服务瓶颈。

**Q：错误率 100%？**  
先用 **接口用例** 单跑确认 Host、Token、断言。

**Q：和 Locust / 独立 SSE 脚本一样吗？**  
平台基于 **接口用例 + asyncio/httpx 自研引擎**。**流式阶段压测**已内置（`stream_burst` 模式 + `qa_sse_v1` 解析器），无需单独跑 Locust；若仍有外部 Locust 脚本，结果需自行对接。

**Q：报告里响应/思考过程被截断？**  
请使用 **Backend + Worker 最新版**（2026-06 起）并 **重新执行压测**；历史记录的 trace 可能仍为旧版截断数据。完整响应采集不影响 QPS/RT。

**Q：单接口请求很多，P95 和 Locust 差很多？**  
报告 **接口维度** 的 P90/P95/P99 基于 **最多 5000 条** 响应时间样本（蓄水池采样，本机与分布式 Worker 均适用），用于控制内存与存储；**总请求数、QPS、错误率、Min/Max 仍统计全部请求**。全局汇总行：新版 Worker 会上报蓄水池样本，Master **合并后重算真分位**；旧版 Worker 无样本时仍回退为各机 P95 加权估算。超大规模压测时，分位仍为近似值，属预期行为；报告页「接口维度详情」上方有说明。

**Q：对比报告变化很大、不可信？**  
请确认：① 两侧总请求不宜过少（建议 ≥50，过少会告警）；② 并发/时长/Ramp-up/热身/**请求间隔（delay）** 等配置一致；③ 配置了 Ramp-up 后，延迟指标默认剔除热身段（可显式设热身为 0 关闭）。QPS 使用有效加压时长作分母，不含结束收尾等待。固定时长压测结束后若仍显示执行中，进度文案为「收尾等待」（在途请求收尾，不再发新请求）。目标 Host 连通性由**执行机**在施压时验证，平台侧不再做 HEAD 预检。

**Q：如何固定「黄金基线」并告警？**  
在报告页点击 **设为基线**，后续同场景报告会自动对比该记录；默认阈值：P95 升高 ≥20%、QPS 下降 ≥15%、错误率升高 ≥5 个百分点时可告警。接口维度 Avg/Min/Max 为全量统计，分位仍受蓄水池上限约束。

**Q：验收目标、基线、错误率熔断有什么区别？**  
**验收目标**判断本次绝对值是否达标（如 QPS≥100）；**基线**判断相对历史钉选记录是否退化；**熔断**是运行中错误率过高自动停。三者独立配置，报告中验收判定为系统确定性结果，AI 只解释、不自造 SLA。

**Q：关了「流式问答」报告里还有 SSE 阶段？**  
不应再有。关闭后会清除 `stream_profile`，当次按普通 HTTP 统计。若仍看到 SSE 区，请确认场景已重新保存并重新执行；执行机提示文案需更新至配套 Perf/Runner 包。

**Q：支持导入 JMeter（.jmx）吗？**  
已支持：在 **接口自动化 → 接口管理 → 导入 → JMeter** 上传 `.jmx`，预览后可生成接口定义、用例、套件；简单 Thread Group 还可勾选生成 **journey 压测场景**（线程数 / Ramp-Up / 时长或循环映射）。含 If/While/Throughput 等控制器或定时器的组会禁用场景生成并说明原因。脚本与复杂控制器不 1:1 还原；CSV 需另行上传绑定。也可继续用 Postman / Swagger / cURL 导入接口。

**Q：能否用一句话生成压测场景？**  
可以。在 **性能测试 → 场景列表 → AI 创建** 输入自然语言（如「用登录链 50 并发压 3 分钟」），可选套件/标签约束。平台只从**项目内已有用例/套件**匹配，生成可编辑草稿，确认后再落库；**不会**编造新接口。无匹配时会提示，不创建空场景。需配置 AI 模型（场景绑定键 `perf_scene_generate`）。
